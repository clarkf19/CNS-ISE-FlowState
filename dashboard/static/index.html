Every request is verified at one enforcement point

Clients never talk to the server directly. Each request passes through the Secure Gateway, where it is authenticated, decrypted, checked for integrity, freshness, session validity and authorization, and then either forwarded or rejected and logged with a reason code.

For every request the server needs assurance that it…

  1. comes from an authenticated clientEd25519 signatures
  2. has not been modified in transitAES-256-GCM tag
  3. belongs to a valid, current sessionSession manager + expiry
  4. has not already been processedNonces, sequence numbers, timestamps
  5. is authorized for its operationRole-based access control

Each problem is matched to a specific mechanism

ProblemMechanismWhy it works
Client impersonationEd25519 digital signaturesOnly the holder of the private key can produce a valid signature; the gateway verifies it with the registered public key.
MITM on key exchangeSigned X25519 ephemeral key exchangeThe shared secret is never transmitted, and signatures from both sides stop an attacker from substituting keys.
Weak or reused keysHKDF-SHA256Strong, independent keys per session and per direction: key separation and forward secrecy.
Eavesdropping and tamperingAES-256-GCM, header as associated dataConfidentiality and integrity together; any modified byte makes the authentication tag fail.
Replay attacksNonces, sequence numbers, timestampsThe gateway remembers what it has processed; duplicate, out-of-order or stale requests are identified.
Session hijacking / reuseCryptographically bound sessions with expiryA stolen session ID is useless without the session keys, and expired sessions are rejected.
Unauthorized operationsRole-based access controlAuthentication proves who the client is; a separate check decides what the client may do.
Undetected attacksSecurity event loggingEvery rejection is recorded with a reason code, making attacks visible and traceable.
